### 暫停後續傳（第 6 項）

- 桌面版暫停時改送 `pause` 指令（取消仍送 `cancel`）。核心收到 `pause` 時，正在下載的檔案先寫入磁碟（`Sync`），再寫出已完成分段清單 `檔名.tmp.part`，保留 `檔名.tmp`。
- 下次接續時，若分段清單屬於同一個 Telegram 檔案（檔案種類與 ID、大小、分段大小相同），且暫存檔確實包含清單列出的分段，就以原檔開啟、只向 Telegram 主資料中心請求缺少的 1 MB 分段；每個分段長度都會核對。不符時清掉舊清單，照舊從頭下載。
- 續傳期間保留舊清單：清單列出的分段不會被改寫，所以中途當機時清單仍然正確。強制結束或斷電時不會產生新清單，該檔案下次從頭下載，不會留下損壞的檔案。
- tdl 下載本來就不使用 CDN（`cdn_supported=false`），所以續傳和一般下載走同一個來源。
- 取消工作、從佇列清除或刪除紀錄時，桌面版刪除該工作逐檔紀錄所列、位於下載資料夾內、且旁邊有 `.tmp.part` 的暫存檔；其他檔案一律不動。命令列模式（沒有桌面版）的 Ctrl+C 行為不變。
- 暫停時的看門狗時限由 3 秒放寬到 10 秒，讓大檔案有時間寫入磁碟；超時被強制結束時，只會退回從頭下載。

### 次要項目

- `BackendBridge.download` 刪除永遠不會執行到的分支。
- 「每次寫入執行 icacls」經查只在保存登入資料與對話清單快取時執行（每次核心操作約兩次），不需處理。
- `app.py`／`backend.py` 過大：本版沒有拆分。大規模搬移程式碼的回歸風險高，且這次要先完成真實帳號驗證，留待之後專門處理。
- 本機舊版 EXE、原始碼 ZIP 與交接檔（1.2.0–1.6.0，37 個、約 737 MB）已移到資源回收筒；刪除前逐一核對 EXE 與 GitHub Release 附件的 SHA-256 相同。

## 相容性

- 1.6.1 以前暫停的工作沒有分段清單，接續時照舊從頭下載該檔案；之後的暫停就會保留分段。
- 退回 1.6.1 時，`.tmp.part` 會被忽略，暫存檔會被覆寫重新下載，不影響正確性。
- 帳號、設定、佇列、紀錄與資料夾格式不變。

## 驗證與交付

以下分為自動化測試、最終 EXE 離線驗證、真實 Telegram 帳號驗證三類，不能互相替代。

**自動化測試（原始碼）**

- 最終建置內完整 Python suite：**218 passed、30 subtests passed**，44.78 秒（1.6.1 為 211 項，新增 7 項）。
- Go：建置腳本列出的桌面、聊天、下載、上傳、轉傳、移轉、訊息、命令與工具套件全部通過；新增續傳（只補缺少的分段、拒收長度不對的分段、只回報完整分段）、暫停保留與取消清除、分段清單不符時重新下載、`pause` 指令、「一般」話題等測試。
- 用模擬核心重現「下載中注入一次 `queue.json` 寫入失敗」：1.6.1 會讓工作失敗，1.6.2 下載照常完成。
- 測試時限實測：故意卡住的測試在時限到時印出堆疊並以錯誤結束。

**最終 EXE 離線驗證（fixture，不連 Telegram）**

- `verification.json`、`restart-verification.json`、`workflow-verification.json`、`batch-forward-verification.json`：獨立目錄啟動、兩個 EXE 程序重開接續、頻道下載與位置記憶、批次轉傳離線流程全部通過。

**真實 Telegram 帳號驗證（使用者同意，使用已記憶帳號的隔離副本）**

- `channel-live-verification.json`（最終 EXE）：取得 650 個對話、包含起迄日的日期篩選與影片篩選正確、實際下載公開 @telegram 影片 1 個（1,842,304 bytes）；原始帳號檔案未改動。
- `resume-live-verification.json`（原始碼後端＋與 EXE 相同的內含核心，SHA-256 相同）：公開 @telegram 影片 8,505,533 bytes，下載到 63% 時暫停，工作狀態為「已暫停」並保留 7 個分段（7 MB）與分段清單；續傳時第一個進度就從 7,456,957 bytes 開始，沒有重抓已保留的分段；續傳完成的檔案與另外直接下載的同一影片 SHA-256 相同（`85cc9c1c…a3b5`），沒有留下暫存檔。
- 同一份收據：批次轉傳**只試跑**（3 則，目的地為使用者的一個非論壇群組），通過；試跑使用不送出的空呼叫，沒有送出任何訊息。原始資料前後雜湊相同。
- 報告不含帳號、對話名稱或媒體內容；隔離副本與下載的影片測完即刪除。

## 已知限制

- 轉傳到「一般」話題的修正沒有用真實帳號實際送出驗證：使用者同意的範圍是批次轉傳只試跑，試跑不會呼叫送出 API。
- 第一次完整測試卡住的原因仍未找到；之後再發生時，新的時限會印出卡住的位置。
- 續傳只適用桌面版的「暫停」與正常關閉；強制結束、斷電或在命令列按 Ctrl+C 仍從頭下載該檔案。
- 接續範圍以 1 MB 分段為單位，暫停當下正在傳輸的分段會重抓。
- EXE 未簽章；上游完整 Go suite 的 Windows `app/update/TestBinaryName` 已知差異未處理。

## 2026-11-10 更正（1.6.4）

1.6.2 的下載佇列沒有「暫停」按鈕。本清冊與當時 README 所說的「暫停」，實際上只有關閉程式時送出的 `pause` 指令；使用者無法單獨暫停一個工作。佇列的「暫停」按鈕與「已暫停」工作的「取消」自 1.6.4 起提供，見 [1.6.4 交接清冊](1.6.4.md)。
