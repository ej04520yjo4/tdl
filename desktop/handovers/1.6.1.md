# 1.6.1 交接清冊

日期：2026-11-02。基底：`codex/group-batch-forward` 的 `bdd223d`（1.6.0，[PR #6](https://github.com/ej04520yjo4/tdl/pull/6) 尚未合併）。功能分支：`claude/desktop-1.6.1-performance`。

## 需求

使用者要求檢查專案可優化與修改的地方，並修正其中最重要的三項：下載進度存檔拖慢下載、佇列為每個檔案建立一列、Go 核心讀取 Telegram Desktop 匯出 JSON 時整份載入記憶體。修第三項時另外找到並修正 JSON 匯入只讀到部分訊息的問題。

## 修改內容

### 1. 下載進度存檔（`desktop/backend.py`）

- 逐檔進度改存在 `accounts/<帳號>/jobdata/<工作>/progress.json`，每個工作一份。`queue.json`、`downloads.json` 只留摘要，改為不縮排的緊湊 JSON。
- 單檔失敗事件不再每筆強制寫入，與一般進度一樣最多 2 秒寫一次；暫停、完成等狀態變更及工作結束時仍立即寫入。
- 舊版寫在 `queue.json`／`downloads.json` 的逐檔紀錄，第一次啟動 1.6.1 時自動搬到各工作資料夾，共用檔中的副本同時移除。工作完成、從佇列清除或從紀錄刪除時，連同工作資料夾一起刪除。
- 存檔仍在讀取核心輸出的執行緒上進行；每次只寫目前工作的資料，沒有另外開背景執行緒。
- 實測（另有 10 個各 2,000 檔的失敗工作）：每次存檔由 0.47–0.69 秒降為 29–86 毫秒（目前工作 500–5,000 檔）；兩個共用檔由 6.6–8 MB 降為不到 0.1 MB。

### 2. 佇列檔案列（`desktop/app.py`）

- 每個工作最多列出 20 個檔案。下載中與失敗的檔案保留原本那一列，不會跳動；20 列用完後，新開始下載或失敗的檔案改用最久沒更新的已完成列（其次是等待中的列）。
- 沒有列出的檔案仍計入上方統計（完成／總數、進行中、失敗、大小、速度、剩餘時間），並顯示「另有 N 個檔案未逐一列出，已計入上方統計」。
- 實測還原 5,000 個檔案的工作：0.89 秒、20,011 個元件、列高 125,101 px，改為 0.03 秒、92 個元件、624 px。

### 3. JSON 匯入（`pkg/tmessage/files.go`）

- 讀取匯出檔開頭的 `id`、`peer_type` 改為同步逐項讀取，讀到 `messages` 就停。Telegram Desktop 官方匯出沒有 `peer_type`，以前會把整個訊息陣列解碼進記憶體，現在不會。
- **修正漏讀訊息：** 舊做法找到 `id`、`peer_type` 後提早離開迴圈，但 jstream 的背景解碼仍繼續讀同一個檔案，和之後從頭重讀訊息清單的流程搶讀。本程式自己的頻道掃描檔正好把這兩個欄位放在 `messages` 前面。離線重現：20,000 則訊息的匯出檔，兩次讀取間隔 0–5 毫秒時只讀到 115 則；200,000 則時間隔 50 毫秒仍只讀到 58 則。實際流程在兩次讀取之間會先查詢對話資訊，間隔長短決定是否發生，檔案越大越容易漏讀。沒有用真實帳號重現。
- 訊息清單解析遇到 JSON 格式錯誤時改為回報錯誤，不再靜默只下載錯誤前讀到的部分。

## 相容性

- 1.6.1 可直接讀取舊版資料並自動搬移逐檔紀錄，未完成工作照常接續。
- 若退回 1.6.0：暫停的工作仍能接續下載，但佇列不會顯示 1.6.1 期間保存的逐檔列（這些列只供顯示，接續範圍由核心的檢查點決定）。
- 截斷或格式錯誤的 JSON 匯入檔，以前可能只下載前段，現在整筆失敗並顯示錯誤。

## 驗證與交付

**自動化測試（原始碼）**

- 最終建置內完整 Python：211 passed、30 subtests passed（43.06 秒）。比 1.6.0 多 4 項：逐檔進度不寫入共用檔、舊版資料搬移、連續失敗不逐筆寫入、5,000 檔佇列最多 20 列且失敗列保留。
- Go：建置腳本列出的桌面、聊天、下載、上傳、轉傳、移轉、命令與工具套件全部通過。`pkg/tmessage` 新增 5 項測試，包含 20,000 則訊息先讀開頭再完整收集訊息、官方匯出不讀訊息陣列、截斷檔回報錯誤。

**最終 EXE 離線驗證（fixture，不連 Telegram）**

- `verification.json`：獨立目錄啟動、核心、繁簡搜尋、畫面繪製與視窗啟閉通過。
- `restart-verification.json`：兩個 EXE 程序驗證關閉保存與同一筆工作接續，重開後佇列仍顯示已完成附件的逐檔列。
- `workflow-verification.json`、`batch-forward-verification.json`：原有頻道下載、位置記憶與批次轉傳離線流程全部通過。
- 收據與畫面：`desktop/verification/1.6.1/`。其中 `queue-5000-files-source-render.png` 是以原始碼繪製的 5,000 檔佇列列，**不是** EXE 截圖；EXE 的離線 fixture 沒有大量檔案的工作。

## 已知限制

- **沒有用真實 Telegram 帳號驗證**；漏讀訊息的修正以離線測試重現與驗證。
- 檢查報告中的第 4–10 項本版未處理：加密失敗時登入資料改存明文、暫停會丟棄下載到一半的檔案、偶發失敗的 UI 測試、`BackendBridge.download` 用不到的分支、每次寫入執行 `icacls`、`app.py`／`backend.py` 過大、驗證截圖進入 git 與本機舊 EXE 佔用空間。
- 暫停與重開仍以附件為單位接續，下載到一半的單一附件會從頭重抓。
- 佇列右側的統計文字最寬 210 px（避免進度更新時列寬跳動）。檔案數到四位數時，開頭的「檔」字可能被截掉；這是既有行為，本版沒有改。
- EXE 未簽章；上游完整 Go suite 的 Windows `app/update/TestBinaryName` 已知差異未處理。
